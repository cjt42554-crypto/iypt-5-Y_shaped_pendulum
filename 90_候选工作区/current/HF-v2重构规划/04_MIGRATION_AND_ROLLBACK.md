# HF-v2 迁移、提升与回滚规划

## 1. 并行而非原位重写

HF-v2 在候选区独立实现。RC1 在以下条件全部满足前保持不变：

- HF-v2 核心 G1–G5 通过；
- 代表性无接触与张力切换基准通过；
- 至少一个接触静态基准通过；
- 三锚点的时间/空间加密完成；
- 公共 API 适配测试通过；
- Pro 完成独立物理和数值审查；
- 用户明确授权修改正式目录。

## 2. 公共接口迁移

现有公共入口是 `HighFidelityModel`、`prepare_initial_state`、`simulate_high_fidelity` 和 `HighFidelityResult`。HF-v2 初期不复制这些大型接口，而使用小型内部合同：

- `HFV2Topology`；
- `HFV2State`；
- `HFV2Model`；
- `StaticSolveResult`；
- `DynamicTrace`；
- `AuditBundle`。

P7 再增加：

- RC1 配置到 HF-v2 配置的只读适配器；
- HF-v2 trace 到 `HighFidelityResult` 或新版本结果类型的适配器；
- API 路由层；
- HDF5 和 UI 适配。

适配器不得包含力学计算。

## 3. 模型选择

正式接入时，RC1 和 HF-v2 必须有不同 `model_id`。建议：

- `HF-DISCRETE-ROD-RIGID-BOB-1.0`：冻结 RC1；
- `HFV2-DISCRETE-CORD-RIGID-BOB-1.0`：通过审查后的新后端；
- 若启用动态硬接触，应在模型身份或接触合同中明确版本。

禁止在原 `model_id` 下用配置布尔值静默替换方程。

## 4. 保留、弃用与删除

### 保留

- RC1 源码和回归测试；
- 既有 HDF5 读取能力；
- 既有历史运行的模型身份；
- 候选接触和资格证据。

### 可标记弃用

只有 HF-v2 正式接入后，才可对 RC1 新运行入口发出弃用提示。弃用提示不能改变旧结果读取。

### 删除

RC1 不在本重构周期内删除。任何删除必须是独立任务，并经过用户明确授权。

## 5. 提升补丁形式

正式提升时不得把候选目录整体复制进正式程序。应形成最小、可审查补丁：

1. 新增 HF-v2 正式包；
2. 新增配置合同；
3. 新增 API 选择；
4. 新增结果适配；
5. 新增测试；
6. 不修改 RC1 方程；
7. 不重写无关 UI、分析和 I/O。

## 6. 回滚原则

HF-v2 的任何阶段都可以通过停止路由到新后端回滚，不需要撤销 RC1。正式接入后若发现问题：

- 默认运行退回 RC1；
- 保留 HF-v2 运行工件和失败证据；
- 不把 HF-v2 结果重标为 RC1；
- 不修改历史 HDF5 的模型身份；
- 修复在独立提交中完成。

## 7. 不兼容性政策

以下差异不是必须修成一致：

- 张力单边模型与双侧压缩正则模型的轨迹差异；
- 原生接触与 guard 终止的差异；
- 群姿态积分与归一化四元数积分的数值差异；
- 新 KKT 静态态与 RC1 无约束静态态的差异。

需要修复的是输入映射错误、单位错误、共享物理项不一致、数值不收敛和违反各自模型合同，而不是所有输出差异。

## 8. Codex 阶段报告模板

每阶段报告至少写明：

- 修改路径；
- 正式目录是否变化；
- 本阶段方程和模型身份；
- 复用的 RC1 公式及其独立验证；
- 新增算法；
- 是否新增 fallback 或特殊 case；
- 已执行命令；
- 通过、失败和未执行的测试；
- 数值结论上限；
- 需要 Pro 裁决的事项；
- 下一阶段是否允许开始。

## 9. 第一轮 Codex 的回滚点

P0/P1 只在候选目录新增文件，因此最坏情况下可以删除候选 `HF-v2-core/` 而不影响正式程序。Codex 不应借机清理、重命名或格式化正式源码。
