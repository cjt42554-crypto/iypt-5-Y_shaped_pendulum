# HF-v2 迁移、提升与回滚规划

## 1. 并行而非原位重写

HF-v2 在候选区独立实现。RC1 在以下条件全部满足前保持不变：

- HF-v2 核心 G1–G5 通过；
- 代表性无接触与张力切换基准通过；
- 至少一个接触静态基准通过；
- 三锚点的时间/空间加密完成；
- 公共 API 适配测试通过；
- Pro 完成独立物理和数值审查；
- 用户明确授权修改正式目录。

## 2. 公共接口迁移

现有公共入口是 `HighFidelityModel`、`prepare_initial_state`、`simulate_high_fidelity` 和 `HighFidelityResult`。HF-v2 初期不复制这些大型接口，而使用小型内部合同：

- `HFV2Topology`；
- `HFV2State`；
- `HFV2Model`；
- `StaticSolveResult`；
- `DynamicTrace`；
- `AuditBundle`。

P7 再增加：

- RC1 配置到 HF-v2 配置的只读适配器；
- HF-v2 trace 到 `HighFidelityResult` 或新版本结果类型的适配器；
- API 路由层；
- HDF5 和 UI 适配。

适配器不得包含力学计算。

## 3. 模型选择

正式接入时，RC1 和 HF-v2 必须有不同 `model_id`。建议：

- `HF-DISCRETE-ROD-RIGID-BOB-1.0`：冻结 RC1；
- `HFV2-DISCRETE-CORD-RIGID-BOB-1.0`：通过审查后的新后端；
- 若启用动态硬接触，应在模型身份或接触合同中明确版本。

禁止在原 `model_id` 下用配置布尔值静默替换方程。

## 4. 工作树保留、Git 历史归档与删除

### 4.1 当前工作树保留

`90_候选工作区/current/` 只保留仍参与现行工作流的内容：

- `HF-v2-core/`：当前物理—数值内核、测试和版本化证据；
- `HF-v2重构规划/`：当前合同、阶段门和 Pro 裁决；
- `无实验参数图谱/`：独立于 RC1 修补链的前向理论参数—图样结果，仍用于研究问题和代表性参数选择。

正式 RC1 源码和回归测试继续保留在 `02_模拟程序/**`，原因是它仍承担：

- 回滚后端；
- 公共 API、配置、I/O 和 UI 的迁移基线；
- HF-v2 与旧后端的表征比较；
- 历史结果的可读取性和模型身份解释。

RC1 是冻结参考，不是 HF-v2 的架构模板。

### 4.2 退出 `current/`、只在 Git 历史保留

以下旧 RC1 候选工作目录已不再被 G2R 或后续 HF-v2 主线直接导入，应退出活动工作树：

- `90_候选工作区/current/三锚点模型阶梯/`；
- `90_候选工作区/current/三锚点高保真资格/`，包括其中的旧 guard、压缩极限和 `hard_contact_candidate` 实验实现。

删除前的完整工作树快照位于提交：

`04149084f5ae12a8da75a8955ab9b74afc95cd87`

这些内容没有从 Git 历史中丢失；需要核对旧结论或提取单个算法原型时，应从该历史提交按路径读取，而不是把整套旧工作重新放回 `current/`。

旧目录的科学结论已经概括写入 `交接说明_history.md`。后续 P3 必须基于 HF-v2 当前拓扑、静态组装和正式接触登记重新建立逐接触约束，不能把旧 `hard_contact_candidate` 直接复制成新后端。P8 的三锚点比较也应由当时通过资格的 HF-v2 重新生成，不能把旧 RC1 候选结果当成新模型证据。

### 4.3 可标记弃用

只有 HF-v2 正式接入后，才可对 RC1 新运行入口发出弃用提示。弃用提示不能改变旧结果读取。

### 4.4 删除边界

RC1 正式程序不在当前重构周期内删除。正式后端的删除必须是独立任务，并经过用户明确授权、迁移测试和回滚审查。

候选工作目录在同时满足以下条件时可从工作树删除：

1. 不被当前合同、测试、证据生成器或下一阶段任务导入；
2. 关键结论已进入全局历史交接；
3. 完整内容仍可由明确 Git 提交恢复；
4. 删除不会改变正式理论、正式程序或当前模型身份。

## 5. 提升补丁形式

正式提升时不得把候选目录整体复制进正式程序。应形成最小、可审查补丁：

1. 新增 HF-v2 正式包；
2. 新增配置合同；
3. 新增 API 选择；
4. 新增结果适配；
5. 新增测试；
6. 不修改 RC1 方程；
7. 不重写无关 UI、分析和 I/O。

## 6. 回滚原则

HF-v2 的任何阶段都可以通过停止路由到新后端回滚，不需要撤销 RC1。正式接入后若发现问题：

- 默认运行退回 RC1；
- 保留 HF-v2 运行工件和失败证据；
- 不把 HF-v2 结果重标为 RC1；
- 不修改历史 HDF5 的模型身份；
- 修复在独立提交中完成。

旧候选目录已退出工作树不影响回滚；必要时可从上述 Git 历史快照恢复特定文件。

## 7. 不兼容性政策

以下差异不是必须修成一致：

- 张力单边模型与双侧压缩正则模型的轨迹差异；
- 原生接触与 guard 终止的差异；
- 群姿态积分与归一化四元数积分的数值差异；
- 新 KKT 静态态与 RC1 无约束静态态的差异。

需要修复的是输入映射错误、单位错误、共享物理项不一致、数值不收敛和违反各自模型合同，而不是所有输出差异。

## 8. Codex 阶段报告模板

每阶段报告至少写明：

- 修改路径；
- 正式目录是否变化；
- 本阶段方程和模型身份；
- 复用的 RC1 公式及其独立验证；
- 新增算法；
- 是否新增 fallback 或特殊 case；
- 已执行命令；
- 通过、失败和未执行的测试；
- 数值结论上限；
- 需要 Pro 裁决的事项；
- 下一阶段是否允许开始。

## 9. 候选核心回滚点

HF-v2 只在候选目录中新增或修改文件，因此当前最坏情况下可以停止路由并删除候选 `HF-v2-core/`，而不影响正式程序。Codex 不应借机清理、重命名或格式化正式源码。
