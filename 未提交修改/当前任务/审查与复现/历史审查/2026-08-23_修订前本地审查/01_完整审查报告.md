## 3. 模型身份修订

### 3.1 已改对的核心点

修订版用不同 ID 区分：

- `FWD-TENSION-CABLE-POINT-BOB-1.1`：仅受拉连续柔索—点摆球；
- `HF-BILATERAL-ROD-RIGID-BOB-1.1`：可拉可压、可弯曲的离散柔性杆—有限刚体摆球；
- `HF-TENSION-ROD-RIGID-BOB-LIMIT-1.1`：仅受拉离散杆受控极限；
- `STRUCTURAL-IDEAL-TORUS-1.1`：结构性理想模型。

这比把所有后端都称作同一个“第一性原理高保真绳模型”更准确。双边杆和仅受拉柔索不是同一连续模型的粗细网格版本，尤其在受压、屈曲、重新受拉和弯曲能显著时，不能强制二者结果一致。

### 3.2 尚未完全落实的地方

- 包目录和部分旧文档仍保留“第一性原理”“高保真”的笼统称呼；
- HF `pyproject.toml` 描述仍写有 `tension-only finite-mass cable simulator`，与双边柔性杆主身份不一致；
- GUI 使用的是新模型 ID，但用户从目录名、启动说明和包元数据仍可能误解后端物理身份；
- 模型身份上限与实际证据状态没有完全联动，详见第 7 节。

因此，“模型身份被定义”已验证，“整个项目所有入口和元数据都一致地贯彻了新身份”只得到部分验证。

## 4. 独立 EI 的实现验证

### 4.1 源码层

修订 overlay 为上支 A、上支 B、下支分别提供独立 `EI`。修订 runner 将这些数值送入 HF 模型，并在运行包中记录实际采用的支路 `EI`。

### 4.2 执行层

本地对 `high_fidelity_independence_torque.yaml` 做了两次同配置短时运行：

- 基线：三支 `EI = 6.75e-6 N·m²`；
- 变体：三支 `EI = 3.375e-6 N·m²`，即基线一半。

两次运行均为：

- 模型：`HF-BILATERAL-ROD-RIGID-BOB-1.1`；
- 网格：`12/12/20`；
- 物理时长：`0.002 s`；
- 接受积分步：1600；
- 输出样本：801；
- 事件数：0。

结果中：

- 基线弯曲能峰值占比：`3.473913483402288e-6`；
- 半 `EI` 弯曲能峰值占比：`1.7698693953711646e-6`；
- 两次摆球位置最大绝对差：`6.192452880391482e-11 m`；
- 能量余额最大绝对残差分别为 `8.216677524401606e-13` 和 `8.222722539962144e-13`。

位置差很小，但严格非零，同时弯曲能响应近似随 `EI` 降低，足以证明 `EI` 不是只写入界面或报告。不过，这个 2 ms 工况的弯曲能极小，不能用它证明独立 `EI` 对目标实验宏观轨迹有显著影响，也不能完成参数辨识或模型选择。

## 5. 测试与可运行性

### 5.1 修订专项测试

修订清单声称 `7 passed`，但仓库没有与该声明绑定的测试日志、JUnit 文件、依赖锁定信息或同提交 CI 状态。本地在实际可用科学 Python 环境中复跑结果为：

```text
5 passed, 2 failed
```

两个失败都落在 `scientific_revision/event_qualification.py` 第 208 行附近：

```python
integrate = getattr(np, "trapezoid", np.trapz)
```

问题是 Python 会先求值 `getattr` 的默认参数，因此即使 `np.trapezoid` 存在，也会先访问已被新 NumPy 移除的 `np.trapz`。兼容写法应避免默认参数的急切求值，例如先检查属性，或直接统一使用项目最低版本已支持的 API。

HF 包依赖只声明 `numpy>=1.26`，没有上界，所以允许安装会触发该失败的新 NumPy；这不是审查环境越界，而是项目声明范围内的兼容性错误。

### 5.2 HF/GUI 完整测试

完整测试共收集 192 项：

```text
182 passed, 10 failed
```

其中：

- 2 项来自新事件资格代码的 `np.trapz` 兼容错误；
- 其余 8 项来自统一后端/平台对冻结前向交付证据的依赖。

新副本的 `configs/unified_shared_forward_case.yaml` 指向 `validation/delivery_root.json`，但该文件未随新副本提交。即使临时链接到原证据，校验仍拒绝运行，错误为 `Forward project root is outside the frozen delivery scope.`。原因是冻结证据把有效范围绑定到原机器绝对路径，而新副本路径不在该范围内。

这说明 `04_...` 不是一个从干净 checkout 就能完整复现统一后端测试的自包含副本。

### 5.3 前向求解器

修订副本中的前向求解器原样复跑：

```text
13 failed, 93 passed, 12 subtests passed
```

失败均与 NumPy 移除 `np.trapz` 有关，集中在柔索和收敛后处理。仅在进程内临时加上兼容别名：

```python
np.trapz = np.trapezoid
```

再次运行得到：

```text

```

这很好地隔离了直接故障原因，但临时 monkeypatch 不等于仓库已修复。修订 GUI 的 worker 会为其启动的前向子进程注入类似兼容处理，所以 GUI 路径可能成功，而独立 CLI、测试和其他调用路径仍会失败。

### 5.4 GUI 启动

修订启动脚本使用：

```sh

```

当前 Ubuntu 主机只有 `/usr/bin/python3`，没有 `python` 命令；直接按脚本执行会得到命令不存在。原项目旧启动器曾显式使用其项目环境，而被复制的新目录不包含被 Git 忽略的虚拟环境。

在显式选择一个已安装依赖的 Python 并用 Xvfb 提供显示后，GUI 可以完成启动冒烟测试。因此 GUI 代码并非完全不可启动，但仓库给出的默认启动入口在该主机上不成立。

## 6. M0–M5 消融框架

`scientific_revision/ablation.py` 能生成 M1–M5 overlay 和清单，生成器本身可执行。M1 overlay 也实际跑通了一次 2 ms 冒烟工况：

- `compression_scale = 0`；

- `effective_claim = MODEL_CONSISTENT`；
- 接受步 1600，样本 801；
- 能量余额最大绝对残差 `3.893780913773791e-11`；
- 状态 `SUCCESS_SINGLE_RUN_GUARDS_UNCERTIFIED`、`NOT_PREDICTIVE`。

但是当前框架仍是“清单级/overlay 级”，主要缺口包括：

1. 没有可执行的 M0 基准配置；
2. 没有一条自动顺序运行 M0–M5 并比较相邻级的 runner；
3. 没有加载并强制共用完整材料状态的实现；
4. 没有机器检查“相邻两级只改变声明的那个机制”；
5. M3 到 M4 除压缩本构外还改变了建议初始剖面，不能据此把差异全部归因于压缩；
6. M5 的空气、支架、接头和观测器多为计划项，不是已经接入的同链机制。

尤其值得注意：M1 overlay 声明 `initial_state_semantics = shared_full_material_state_required`，但实际 HF runner 仍采用 `geometric_direct_release_non_equilibrium` 的后端初态准备，并没有导入一个跨模型共用的完整材料状态。因此“要求同初态”目前是标签，不是已执行约束。

## 7. 事件资格认证与证据等级

### 7.1 事件资格程序的实际能力

当前工具可以读取若干既有运行，提取事件、轨迹、峰值张力、一个张力积分和能量残差，并进行成对阈值比较。这作为比较器是有用的，但不能独立认证运行矩阵。

它没有验证：

- 空间网格确为 `N/2N/4N`；
- 时间步、容差和输出采样确实按计划加密；
- 所有运行使用同一配置、模型、overlay、求解器和初态，仅改变指定数值参数；
- 输入文件和阈值文件在运行前已经冻结；
- 事件身份在不同网格间做了支路、材料位置和方向匹配。

程序只要从计划文件读到阈值，就把输出写成 `thresholds_source = pre_frozen_plan_file`。这只能证明阈值来自该文件，不能证明该文件确实早于所有运行被冻结。

此外，当前所谓 `tension_impulse` 是在整个记录窗口内，对“所有支路/材料段中的最大张力”随时间积分；它不是某一失张或重新受拉事件附近、某一指定支路和材料位置的局部冲量。对事件尖峰收敛而言，这个定义需要修改。

因此事件资格状态必须判为 `NO_GO`，而不是“框架已有，所以事件工况已认证”。

### 7.2 `CODE_VERIFIED` 不是证书

overlay 的有效声明本质上是“用户请求等级”和“模型身份上限”的较小者。`model_identity.py` 中虽有 `evidence_transition_allowed()`，但 runner、overlay 和 GUI 没有用它强制控制输出等级。

可构造一个双边有限刚体 HF overlay：

- 请求 `CODE_VERIFIED`；
- `contact_guard_mode = disabled`；
- 不提供绿灯测试或资格矩阵证据；

仍得到 `effective_claim = CODE_VERIFIED`。

所以该字段当前应理解为“声明上限标签”，不能当作同提交代码已验证证书。正确做法是让声明由机器可验证的测试清单、输入哈希、运行矩阵和阈值冻结证据生成；缺项时自动降级。

## 8. 输入封存与 TOCTOU

GUI worker 在排队时记录 overlay 路径和 SHA-256，子进程启动前也会重算一次 SHA-256。这比完全不校验好，但仍有时间检查—时间使用间隙：

1. worker 校验路径内容；
2. worker 启动 `run-hf` 子进程；
3. 子进程按路径再次打开 overlay；
4. 文件若在第 1、3 步之间改变，实际使用内容可能不是刚才校验的内容。

更稳妥的方法是把已校验的 overlay 字节复制进任务不可变暂存区，让 runner 读取该副本，并同时记录其 SHA-256。独立 CLI 运行包也应记录 overlay 内容哈希，而不是只记录路径或解析值。

## 9. 结构性理论证据审计

结构性审计工具对仓库现有 `structural_analysis_results.json` 成功运行，共审计 3 个案例：

- `numerically_tuned_compensation`：`NUMERICALLY_SUPPORTED_FINITE_WINDOW_CLOSURE`；
- `quartic_normal_form_compensation`：`FINITE_WINDOW_DIAGNOSTIC_ONLY`；
- `zero_amplitude_geometry`：`FINITE_WINDOW_DIAGNOSTIC_ONLY`。

三者均没有被标记为：

- 已证明锁频；
- 已证明不变环面；
- 已证明连续振幅参数域。

这是修订中较扎实的一部分。它正确地区分“有限窗轨迹接近闭合”和更强的动力系统结论。仍需注意：审计器能阻止过度表述，不会自动把有限网格数值证据提升为数学证明。

## 11. 为什么没有继续跑生产长时 HF

本次确实运行了三次可执行 HF 短时工况，用来验证路径、参数注入和受控极限；没有运行完整生产网格长时资格矩阵，原因不是认为它不重要，而是当前更前置的门槛已经失败：

- 专项测试不绿；
- 完整测试不绿；
- 新副本不自包含；
- 事件资格程序本身不能验证计划身份；
- M0–M5 共初态链未完成。

在这些问题未修复前只跑一次昂贵长时 HF，最多得到一个单次轨迹，不能得到空间、时间、输出带宽、求解器和事件量都收敛的资格结论。正确顺序是先使代码和证据链可判定，再冻结并运行完整矩阵。

## 12. 实验预测状态

仓库中增加了材料与实验协议模板，但本次没有发现或运行以下完整证据：

- 三支独立 `EA`、`EI` 和黏弹/滞回标定；
- 结内吸收长度、滑移、接头刚度和支架柔度标定；
- 摆球质心、惯量、连接点和相机模型标定；
- 严格分开的 `CALIBRATION / VALIDATION / PREDICTION_HOLDOUT` 数据；

所以当前可以说“模型和代码正在向可检验预测推进”，不能说“已经具有经证实的预测能力”。数值自洽、代码通过测试、离散收敛、实验有效和盲预测是五个不同门槛。
