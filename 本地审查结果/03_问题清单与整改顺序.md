# 问题清单与整改顺序

## 1. 总体策略

建议保留 Pro 修改中正确的模型身份、独立 `EI` 和科学显示护栏，不要把 `04_审查后修订版_2026-08-23/` 整体删除。应新增一个纠正提交，先恢复仓库边界和绿灯测试，再完成证据链，最后才投入生产 HF 与实验验证。

优先级含义：

- P1：阻止当前版本被接受、阻止数值资格或造成关键科学声明失真；
- P2：不一定改变主物理结果，但影响可运行性、可复核性或用户理解；
- P3：维护性和长期质量问题。

## 2. P1 问题

### P1-01 恢复被删除的原根目录归档

现状：提交 `5cf8e2f3...` 删除了 `01_最终理论.tar.xz`，违反用户要求的“只新增文件夹”。

整改：

1. 从 `bd1066c9...` 精确恢复该归档；
2. 验证恢复后对象哈希与原提交相同；
3. 修正 `REVISION_MANIFEST.json` 的基线叙述，不再把删除后的提交当作整个操作的原始基线；
4. 用路径级差异证明除新目录和恢复动作外没有修改原文件。

验收：从 `bd1066c9...` 到纠正后提交，排除允许新增目录后，原有路径没有删除或修改。

### P1-02 修复 NumPy 兼容并让全部测试绿灯

现状：修订专项 `5 passed, 2 failed`；前向原样 `13 failed, 93 passed`；根因是 `np.trapz` 在新 NumPy 中移除，以及 `getattr` 默认参数急切求值。

整改：

1. 在事件资格工具中使用不会先访问缺失属性的兼容实现；
2. 统一替换或封装前向求解器所有积分 API；
3. 不只在 GUI worker 子进程中 monkeypatch；
4. 用最低支持 NumPy 和当前最新版 NumPy 做矩阵测试；
5. 将完整测试结果绑定到同一个 Git 提交。

验收：修订专项、前向完整套件、HF/GUI 完整套件在声明支持的依赖范围内全部通过，无 xfail 掩盖。

### P1-03 重建自包含、可移植的冻结交付证据

现状：新副本缺 `validation/delivery_root.json`；原证据又绑定原机器绝对交付范围，导致 8 项完整测试失败。

整改：

1. 为新副本重新生成冻结交付包；
2. 让证据以内容哈希和仓库内相对身份为核心，避免不可移植绝对路径；
3. 保留完整链校验，不得通过删除范围检查来“修测试”；
4. 增加干净 clone/check-out CI，从零安装后运行统一后端测试。

验收：在任意新目录 checkout 同一提交，所有冻结链和统一后端测试通过，且篡改任一载荷会失败关闭。

### P1-04 把事件资格比较器升级为真正的资格执行链

现状：工具只比较已有运行，不能证明矩阵成员身份，自动把计划文件称为“预冻结”，张力冲量也不是事件局部定义。

整改：

1. 资格计划必须预先生成不可变 ID 和哈希；
2. runner 根据计划直接生成全部运行，不接受事后任意目录拼装；
3. 每个成员绑定模型、配置、overlay、初态、网格、求解器、容差、输出间隔和代码提交；
4. 自动验证 `N/2N/4N`、时间/容差、输出带宽和求解器轴只改变声明字段；
5. 事件按支路、材料坐标、类型、方向和序号匹配；
6. 冲量改为预定义事件窗内、指定支路和材料位置的有物理含义积分；
7. 事件缺失、顺序改变或无法匹配时失败关闭，不用零值填补；
8. 阈值冻结时间和运行开始时间进入签名或不可变清单。

验收：用一个故意错网格、错 overlay、事后改阈值和错事件匹配的负测试矩阵，工具必须全部拒绝。

### P1-05 让证据等级由机器证据生成

现状：`CODE_VERIFIED` 可通过配置请求得到；`evidence_transition_allowed()` 没有进入 runner/GUI 的强制路径；禁用接触护栏仍可能显示 `CODE_VERIFIED`。

整改：

1. 用户输入只能请求分析目标，不能直接赋予证据等级；
2. 证据状态由同提交测试清单、输入身份、数值资格和实验结果计算；
3. `contact_guard_mode = disabled`、脏工作树、缺哈希、缺测试或单次运行必须自动降级；
4. `MODEL_CONSISTENT / CODE_VERIFIED / NUMERICALLY_QUALIFIED / EXPERIMENTALLY_VALIDATED / PREDICTIVE` 每次跃迁都要有强制条件；
5. 报告同时显示“模型允许的理论上限”和“当前证据实际达到的等级”，不得混为一个字段。

验收：构造缺证据和关闭护栏的 overlay，输出不能达到 `CODE_VERIFIED`；只有绑定的全绿证据才允许升级。

### P1-06 实现真正可执行的 M0–M5 消融链

现状：当前主要生成 M1–M5 overlay/清单；无 M0、无共用完整材料状态加载、无链式 runner/比较器、无相邻单变化强制。

整改：

1. 定义可运行 M0 和所有 M1–M5 基础配置；
2. 生成一个完整材料坐标初态，明确哪些模型变量可映射、哪些不可映射；
3. 让所有可比较级读取同一冻结初态；
4. 对相邻级做 schema diff，只允许白名单机制变化；
5. 将 M3→M4 的初态剖面变化拆成单独级，避免与压缩本构同时变化；
6. M5 只有在空气、支架、接头和观测器真实接入时才能标记完成；
7. 自动输出每一级相对前一级的轨迹、事件、频率、能量和残差差异。

验收：一条命令生成并执行全链；任意额外参数漂移会被机器拒绝；每一级都有真实运行产物而非只有 manifest。

### P1-07 修复 overlay 封存的 TOCTOU 间隙

现状：worker 校验路径哈希后，子进程再次按原路径读取，中间存在被替换窗口；CLI 运行包也没有统一记录 overlay 原始字节 SHA-256。

整改：

1. 排队时把已验证字节复制到任务不可变暂存区；
2. runner 只读取该副本；
3. 将原始字节、解析后规范表示和二者哈希写入运行包；
4. 加入在校验与启动间替换源文件的并发负测试。

验收：无论原路径随后如何变化，任务使用的都是已封存内容；报告可以从哈希追溯到实际字节。

## 3. P2 问题

### P2-01 修复默认 GUI 启动入口

现状：脚本调用不存在的 `python` 命令，新副本又不带原虚拟环境。

整改：使用可解析的项目 Python，例如优先仓库环境后回落 `python3`，启动前检查依赖并给出明确安装命令。不要静默调用系统中不确定的解释器。

验收：在当前 Ubuntu 干净 shell 中按 README 命令可启动；缺依赖时明确失败，不出现模糊导入错误。

### P2-02 统一命名和包元数据

现状：GUI 新标签正确，但目录、旧文档和 `pyproject.toml` 仍混用“第一性原理”“tension-only cable”“高保真”。

整改：统一为物理身份明确的名称；若保留“高保真”，必须紧邻说明它是离散柔性杆后端，是否更接近实验需要模型选择验证。

验收：GUI、CLI、包描述、README、运行报告和模型清单对同一后端使用一致身份。

### P2-03 让清单声明可复核

现状：`REVISION_MANIFEST.json` 写 `7 passed`，但无命令、环境、日志、退出码或 CI 绑定。

整改：清单只引用机器生成的测试证据；记录命令、收集数、退出码、依赖锁、平台、提交和证据文件哈希。历史结果必须标日期和提交，不覆盖为当前状态。

验收：删除或修改测试证据后，清单校验失败；任何人能在干净环境复跑同一口径。

### P2-04 清理 Ruff 错误

现状：新修订源文件和测试有 12 项 Ruff 错误。

整改：修复未使用导入、导入排序、现代类型注解和 `zip(strict=...)` 等问题，并在 CI 中加入 lint。

验收：Ruff 对声明范围零错误，不以全局忽略绕过。

## 4. P3 问题

### P3-01 性能证据规范化

区分 solver CPU/内部计时、worker 总时间和外部墙钟时间；记录硬件、线程、BLAS、Python/NumPy/SciPy 版本。不要横向比较不同计时口径。

### P3-02 报告与原始运行产物的长期绑定

所有 Markdown 摘要应从不可变运行包机器生成或引用其哈希，避免手抄数字漂移。临时目录路径不得作为长期身份。

### P3-03 增加负测试和科学失败示例

至少覆盖负张力、事件丢失、事件顺序改变、阈值后改、overlay 替换、绝对路径漂移、短频率窗、搜索边界峰、模型身份不兼容和实验数据集混用。

## 5. 推荐实施顺序

```text
阶段 A：仓库与代码门槛
  1. 恢复 01_最终理论.tar.xz
  2. 修 NumPy 兼容
  3. 修干净 checkout 冻结交付链
  4. 修启动器、元数据和 lint
  5. 加同提交 CI，完整测试全绿

阶段 B：科学证据链
  6. 实现证据等级状态机
  7. 封堵 overlay TOCTOU
  8. 实现共初态 M0–M5 全链
  9. 实现预冻结事件资格执行器和事件局部指标

阶段 C：生产数值资格
  10. 冻结目标工况、阈值和资源计划
  11. 跑 N/2N/4N、时间/容差、输出带宽、求解器矩阵
  12. 单独认证失张、重新受拉、压缩和屈曲事件

阶段 D：实验预测
  13. 独立标定 EA/EI/黏弹/结/支架/摆球/相机
  14. 只用 CALIBRATION 拟合
  15. 用 VALIDATION 做模型选择和误差诊断
  16. 冻结后对 PREDICTION_HOLDOUT 做盲预测
```

阶段 A 未通过前不应花费大量算力跑阶段 C。阶段 C 通过也不能跳过阶段 D；数值收敛只说明离散实现稳定，不说明物理模型对实验正确。

## 6. 最低接受门槛

纠正版本至少满足以下条件，才可从 `PARTIAL` 升为“代码已验证、可进入生产资格”：

- 原根目录边界恢复且有 Git 对象证据；
- 所有声明支持的环境中测试全绿；
- 干净 checkout 可复现统一后端；
- 证据等级不可由配置自封；
- M0–M5 共初态和单变量差分可执行；
- 事件资格计划、输入和阈值在运行前不可变；
- 所有运行失败关闭并保留原始证据；
- 同提交 CI 和本地证据一致。

达到这些条件后，状态仍只能是：

```text
CODE_VERIFIED
READY_FOR_NUMERICAL_QUALIFICATION
NOT_EXPERIMENTALLY_VALIDATED
NOT_PREDICTIVE
```

只有生产矩阵和实验留出验证分别通过，后两个状态才允许升级。
